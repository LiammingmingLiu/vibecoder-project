§1一页概览

产品一句话：下班回家想打游戏没搭子？打开网页，用一句话说出你想玩什么、想找什么样的人，回车，30 秒内匹配到一个搭子，直接在站内聊起来、约起来 —— 「游戏版 Soul」。

本次交付物：一个部署在 Vercel 上的可交互 Web Demo（暂定名「游戏搭子」，正式名见 §13-Q1），移动端优先，支持多台设备真实互相匹配和实时聊天，配 24 个 AI 扮演的种子用户兜底，保证现场演示任何情况下不冷场。

维度决定
形态Web（手机浏览器打开即用，无需装 App、无需注册）
核心闭环Onboarding 建画像（可跳过）→ 自然语言输入需求 → LLM 解析 + 匹配 → 结果卡片（含「为什么是 TA」）→ 站内 IM 开聊
技术栈Next.js 15 + TypeScript + Tailwind · GSAP（动效编排）· Vercel · Supabase（Postgres + Realtime）· Claude API
演示高潮两台真机现场互配成功 + 匹配理由卡片瞬间点亮
不做陪玩交易、支付、实名审查、真实游戏账号 OAuth（愿景页展示即可）

§2会议决议提炼

以下是 7/25 讨论中已达成共识的点，编码时视为约束；未达成共识的见 §13。

做什么

  • 共识自然语言是唯一的匹配入口。不做一堆筛选按钮，一个输入框像跟 Codex 对话一样，三类用户状态（①不知道玩什么 ②明确玩某游戏 ③明确游戏且对人有要求）全部用一句话表达，交给模型解析。
  • 共识匹配成功后进入站内 IM。不依赖微信群、不依赖游戏内语音；想加什么好友让用户在聊天里自己交换。聊天记录持久保留（像微信，不阅后即焚），长期可沉淀为画像。
  • 共识Onboarding 是可选项（option）。想要精准匹配就多填（游戏、段位/KDA、位置、风格激进或保守、性别、声音、MBTI、星座），想随缘就跳过直接随机匹配。
  • 共识标签体系为画像服务。游戏玩家看不到脸，最关心的是：性别、声音、技术（数据面板）、玩什么游戏。游戏账号绑定（三角洲 / 瓦 / Steam 库）是正式版的杀手锏，Demo 阶段做成愿景展示。
  • 共识商业化走轻订阅：Pro 会员解锁性别筛选、声音筛选、仅匹配认证真人、每日次数上限提升。定价锚点 ~10 元/月。Demo 里做一个假的 Pro 弹窗讲故事即可（可选，见 §10-M5）。

明确不做

  • 排除陪玩平台 / 交易撮合——售后、审查、责任界定问题太多，一旦碰就是另一个故事。
  • 排除本期任何真实收费、支付通道。
  • 排除Demo 阶段的真实游戏 API / Steam OAuth（三角洲无公开 API；Steam Web API 国内访问不稳，现场演这个是给自己挖坑，见 §12）。
  • 排除语音上传/录音（正式版再说；Demo 用「声音标签」代替：低音炮 / 御姐音 / 少年音 / 奶音…）。

§3演示脚本（5 分钟 Storyboard）

Demo 是为「演」而生的，先定演法再写代码 —— 每个 beat 对应的功能就是开发的优先级。

  1. 0:00–0:30
    痛点开场（口播）「晚上十点，你想打两把三角洲，固定搭子今晚有事。你会去小红书搜群、加群、爬楼、加微信……还是打开它？」投屏主界面。
  2. 0:30–1:30
    Onboarding（真机 A，投屏）队友 A 手机现场输入昵称，快速点选：三角洲 · 突击位 · 打法激进 · 晚间在线 · 低音炮。强调「全部可跳过」。
  3. 1:30–2:30
    自然语言匹配（真机 B，投屏）主讲手机输入：「想找个女生一起玩三角洲，我打突击她打支援，最好声音好听点，现在就能上号」。点「开始匹配」→ 屏幕流式显示解析出的标签（游戏=三角洲、性别=女、位置互补、时段=现在）。
  4. 2:30–3:00
    Aha 时刻：匹配卡片翻牌动画弹出对方卡片，重点念出「为什么是 TA」：「你们都主玩三角洲，TA 常驻支援位和你互补，最近 7 天都在 22 点后活跃」——这句话是全场记忆点。
  5. 3:00–4:00
    双端实时聊天A、B 两台真机互发消息，投屏展示秒级到达；顺手展示一个 bot 搭子的聊天（证明冷启动期也永远有人陪）。
  6. 4:00–4:30
    愿景页一屏讲三件事：游戏账号绑定（Steam 库 / KDA 自动成为标签）、认证真人、Pro 轻订阅 ~10 元/月。
  7. 4:30–5:00
    收尾 + 观众参与（可选）放出二维码让观众进场匹配（是否开放见 §13-Q2）。
双保险整场演示设计为「真人互配为主、Bot 兜底为辅」：任何一台真机掉链子，匹配池里 24 个 AI 扮演的用户保证 3 秒内必出结果、聊天必有回应（§9）。彩排模式开关见 §12。

§4界面与交互规格

共 3 个核心界面 + 1 个愿景页，移动端优先（375px 起），桌面居中卡片布局。深色游戏夜场风格，主色自定（避免紫色渐变烂大街配色）。全站中文。全站动效由 GSAP 统一编排，逐场景规格见本节末尾「动效规格」。

S1 · Onboarding /onboarding

  • 输入昵称（必填，2–12 字符）→ 生成本地会话（UUID 存 localStorage，无注册无密码）。
  • 可选标签，全部为点选芯片（chip），零打字：常玩游戏（三角洲行动 / 无畏契约 / 英雄联盟 / 王者荣耀 / 原神 / CS2 / 永劫无间 / Steam 杂食，多选）、擅长位置/角色（按所选游戏动态出现）、打法风格（激进 / 稳健 / 娱乐）、性别（男 / 女 / 保密）、声音标签（低音炮 / 少年音 / 御姐音 / 甜妹音 / 不开麦）、常在线时段（下午 / 晚间 / 深夜 / 周末）、MBTI（可选）。
  • 右上角「跳过」始终可见；完成或跳过后进入 S2。已有会话的用户直接进 S2（右上角头像可回来改资料）。

S2 · 主界面（匹配）/

  • 结构极简：一句 slogan + 一个多行输入框（placeholder 轮播三类示例文案，对应三类用户状态）+ 一个大按钮「开始匹配」。
  • 点击后进入匹配动画态：流式展示两步 —— ①「理解你的需求…」逐条点亮解析出的标签芯片；②「正在为你翻牌…」雷达扫描动画。GSAP 时间轴编排（见动效规格 A2/A3），全程 ≤ 6 秒（含 LLM 延迟），超时走兜底（§12）。
  • 结果卡片：对方昵称、标签芯片（游戏/位置/风格/声音/时段）、在线状态点、以及重点样式的「为什么是 TA」两行理由。按钮：「开聊」→ S3；「换一个」→ 重新匹配（同一请求最多换 3 次，每次排除已出现的人）。
  • 匹配不到完全符合的人时永不返回空态：降级为最接近的人选，理由里诚实说明（「没找到常玩三角洲的女生，TA 是最接近的：…」）。
  • 底部一行小字入口：「未来：绑定 Steam / 游戏账号，战绩自动变标签 →」打开愿景页弹层。

S3 · 聊天 /chat/[matchId]

  • 顶部：对方昵称 + 标签摘要 + 「为什么匹配」可展开回看。消息气泡区 + 底部输入框，回车/按钮发送。
  • 实时性：Supabase Realtime 订阅新消息；若 NEXT_PUBLIC_POLL_MODE=1 则降级为 1.5s 轮询（现场网络不稳时的开关，UI 无感知）。
  • 对方为 bot 时自动回复（§8-C），带 1–3 秒拟人延迟和「对方正在输入…」指示。
  • 快捷短语条：「上号？」「加个游戏好友」「开麦吗」—— 降低现场演示打字成本。
  • 左侧（桌面）/入口（移动）显示「我的搭子」列表：历史 match 会话可重进（聊天记录持久，呼应 §2）。

S4 · 愿景弹层

  • 三卡片：①账号绑定（Steam 库存 · 时长 · KDA 自动成为可信标签）②认证真人 & 安全（举报/拉黑）③Pro 订阅 ~10 元/月（性别/声音筛选 · 无限次匹配）。纯静态展示，按钮点击显示「Coming soon」。

动效规格（GSAP 编排）

动效是本 demo 的第二主角：匹配序列的「仪式感」直接决定 §3 aha 时刻的成色。统一使用 GSAP 3.13+（自 2025 起完全免费、含全部官方插件）+ 官方 React 集成 @gsap/react 的 useGSAP hook（自动清理，StrictMode 安全）。逐场景编排如下：

#场景编排技术点
A1S1 标签点选芯片点选瞬间 scale 1→1.15→1 微弹，选中态描边亮起；分组区块进场时轻微错峰上浮gsap.to，微交互 0.18s
A2S2 需求解析点击匹配后输入框上浮收纳至顶部；解析出的标签芯片随 SSE 事件逐个弹入（scale 0.6→1 + y 8→0，back.out(1.7)，相邻错峰 ≥80ms）事件驱动 gsap.from——动画跟数据走，不做假等待
A3S2 翻牌（aha）雷达扫描线 360° 循环（repeat:-1）→ 收到 matched 事件后停针、扫描圈收缩，卡片 3D 翻转入场（rotationY -90→0，transformPerspective:800，0.6s power4.out）+ 阴影抬升主 timeline 串联；翻转全序列 ≤1.2s
A4S2 匹配理由「为什么是 TA」文案按行浮现（y 12→0 + opacity，行间 stagger 0.12s）——把全场最重要的两行字「念」出来SplitText（已免费）按行切分
A5S3 聊天新气泡从发送侧入场（y 16 + scale .92→1）；「对方正在输入」三点循环 timeline；快捷短语条首次进入时 slide-in只动画新增消息，禁止整列表重排
A6S4 愿景弹层遮罩 fade + 三卡片 y 24 依次上浮（stagger 0.08s）一条 timeline
  • 性能红线：只动 transform / opacity（保移动端 60fps）；循环动画随组件卸载清理（useGSAP 托管）；prefers-reduced-motion 用户直接呈现终态（gsap.matchMedia）。
  • 节奏基准：微交互 0.15–0.25s、入场 0.4–0.6s；动效为演示节奏服务，不得拖慢 §11 的 6 秒匹配红线——动画永远等数据，数据永远不等动画。

§5技术架构

手机/电脑浏览器 (Next.js 前端, Vercel CDN)
      │
      ├── POST /api/match  (SSE 流式) ──► Vercel Serverless Function
      │                                     ├─► Claude API ① 解析需求 → 结构化 JSON
      │                                     ├─► Supabase SQL 预筛候选 (游戏交集/在线)
      │                                     └─► Claude API ② Top-K 重排 + 生成匹配理由
      ├── /api/profile · /api/messages ──► Vercel Serverless ──► Supabase Postgres
      │
      └── 聊天实时订阅 ◄────────────── Supabase Realtime (WebSocket, 托管)
                                          ▲
          bot 自动回复：POST /api/messages 时若对方 is_bot，
          服务端调 Claude API ③ 生成人设回复后延迟写入 ────┘

选型理由（给编码代理的硬约束）

  • Next.js 15（App Router）+ TypeScript + Tailwind，部署 Vercel：一个仓库前后端全包，git push 即部署，符合「后端用 Vercel」的决定。
  • 状态必须落 Supabase（Postgres），严禁内存存储。Vercel Serverless 每次调用可能是不同实例，进程内 Map/全局变量在本地 dev 能跑、上线必炸 —— 这是本项目最大的隐形坑，见 §14 约束 C1。
  • 聊天用 Supabase Realtime（Postgres CDC 订阅），不要自建 WebSocket：Vercel Serverless 不支持长连接 WebSocket 服务端。保留轮询降级开关。
  • LLM 用 Anthropic 官方 TS SDK @anthropic-ai/sdk，只在服务端调用（API Key 绝不进前端）。模型与参数规格见 §8。
  • 动效用 GSAP（gsap + @gsap/react）而非 CSS animation / Framer Motion：匹配序列是一段需要与 SSE 数据流联动的多步编排（收纳→芯片弹入→雷达→翻牌→理由逐行），timeline 的串联、中断与跳帧能力是 CSS 做不到的；GSAP 3.13 起全插件免费（含 SplitText）。动画组件必须 "use client"，规格与红线见 §4 动效规格。
  • 无鉴权体系：昵称 + localStorage UUID 即身份（demo 专用；正式版换 Supabase Auth）。
网络警告*.vercel.app 域名在国内直连不稳定。演示机与参与真机务必走热点/代理（§12-R3）；若要开放观众扫码，先在会场实测（§13-Q2）。

§6数据模型

Supabase SQL Editor 直接执行。Demo 用 anon key + 宽松 RLS（全表可读写）换开发速度，正式版必须收紧。

create table profiles (
  id uuid primary key default gen_random_uuid(),
  nickname text not null,
  gender text default 'secret',          -- male | female | secret
  voice_tag text,                        -- 低音炮/少年音/御姐音/甜妹音/不开麦
  games jsonb default '[]',              -- [{"name":"三角洲行动","roles":["突击"],"rank":"钻石"}]
  play_style text,                       -- 激进/稳健/娱乐
  active_hours text[] default '{}',      -- {下午,晚间,深夜,周末}
  mbti text,
  intro text,                            -- bot 人设简介，真人可留空
  is_bot boolean default false,
  last_seen_at timestamptz default now(),
  created_at timestamptz default now()
);

create table match_requests (
  id uuid primary key default gen_random_uuid(),
  requester_id uuid references profiles(id),
  raw_text text not null,                -- 用户原话
  parsed jsonb,                          -- LLM 解析结果（§8-A 的 schema）
  excluded_ids uuid[] default '{}',      -- 「换一个」已排除的人
  created_at timestamptz default now()
);

create table matches (
  id uuid primary key default gen_random_uuid(),
  request_id uuid references match_requests(id),
  user_a uuid references profiles(id),
  user_b uuid references profiles(id),
  reason text not null,                  -- 「为什么是 TA」
  score numeric,
  created_at timestamptz default now()
);

create table messages (
  id bigint generated always as identity primary key,
  match_id uuid references matches(id),
  sender_id uuid references profiles(id),
  content text not null,
  created_at timestamptz default now()
);
create index on messages (match_id, id);
alter publication supabase_realtime add table messages;  -- 开启实时订阅

§7API 设计

路由方法说明
/api/profilePOST创建/更新画像。入参 = profiles 字段子集；返回 { id }，前端存 localStorage。
/api/matchPOSTSSE 流式。入参 { profileId, text, excludeIds? }。事件序列：parsing（解析出的标签，逐个推）→ searching → matched（{ matchId, partner, reason, score }）→ done；错误发 fallback 事件（§12）。
/api/messages?matchId=GET拉取历史消息（轮询模式下带 afterId 增量拉取）。
/api/messagesPOST{ matchId, senderId, content } 写库；若对端 is_bot=true，服务端异步生成 bot 回复（§8-C，延迟 1–3s 写入，勿阻塞本次响应）。
/api/matches?profileId=GET「我的搭子」列表（含最后一条消息预览）。

匹配管线（/api/match 内部）

  1. 解析：Claude 调用 ①（§8-A）把 text 变成结构化条件，边流边推 parsing 事件。
  2. SQL 预筛：候选 = 非本人、未被排除的 profiles，按「游戏交集 > 时段匹配 > 最近活跃」粗排取 Top 12（真人优先于 bot：order by is_bot asc, last_seen_at desc）。
  3. LLM 重排：Claude 调用 ②（§8-B）从 12 人中选 1 + 写理由；写入 matches 表，推 matched。
  4. 永不空手：候选为空时放宽条件重筛（去掉性别/声音要求 → 去掉游戏要求），理由中如实说明降级。

§8LLM 调用设计

调用模型要点
A · 需求解析claude-opus-4-8结构化输出（json_schema），流式，max_tokens 2048
B · 重排 + 理由claude-opus-4-8结构化输出，max_tokens 2048，理由 ≤ 60 字、口语化
C · Bot 人设回复claude-haiku-4-5低延迟低成本闲聊；max_tokens 300；回复 ≤ 40 字
参数红线Opus 4.8 禁止传 temperature / top_p / top_k / budget_tokens（会直接 400）；需要思考深度用 thinking: {type:"adaptive"}。结构化输出用 output_config.format（json_schema），不要用已废弃的顶层 output_format。API Key 只放服务端环境变量 ANTHROPIC_API_KEY。

A · 需求解析 → JSON

import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic(); // 读 ANTHROPIC_API_KEY

const PARSE_SCHEMA = {
  type: "object",
  properties: {
    games:        { type: "array", items: { type: "string" } }, // 空数组=不限
    partner: { type: "object", properties: {
      gender:     { type: "string", enum: ["male","female","any"] },
      roles:      { type: "array", items: { type: "string" } },  // 期望对方位置
      voice:      { type: "string" },                            // ""=不限
      style:      { type: "string", enum: ["激进","稳健","娱乐",""] }
    }, required: ["gender","roles","voice","style"], additionalProperties: false },
    my_roles:     { type: "array", items: { type: "string" } },
    time:         { type: "string", enum: ["now","tonight","weekend","any"] },
    mode:         { type: "string", enum: ["specific","random"] } // random=随缘匹配
  },
  required: ["games","partner","my_roles","time","mode"],
  additionalProperties: false
};

const resp = await client.messages.create({
  model: "claude-opus-4-8",
  max_tokens: 2048,
  system: "你是游戏搭子匹配平台的需求解析器。把用户的中文自然语言需求解析为结构化条件。用户没提到的维度一律用宽松默认值(any/空)，不要脑补。游戏名归一化到平台词表：三角洲行动、无畏契约、英雄联盟、王者荣耀、原神、CS2、永劫无间。",
  output_config: { format: { type: "json_schema", schema: PARSE_SCHEMA } },
  messages: [{ role: "user", content: text }],
});

B · 重排 + 匹配理由

  • 输入：解析结果 JSON + 候选 12 人的画像 JSON（含 id）。输出 schema：{ chosen_id, score(0-100), reason }。
  • System 要点：「优先硬条件（游戏、性别）→ 软条件（位置互补、时段重叠、风格）；reason 用第二人称、≤60 字、必须引用双方真实标签，禁止编造；条件被降级时 reason 首句如实说明」。

C · Bot 人设回复

  • System = 该 bot 的 intro 人设 + 通用规则：「你在搭子平台闲聊，中文口语、≤40 字、一次一句、偶尔用游戏黑话；目标是把话题引向约一局游戏；绝不暴露自己是 AI，除非被直接问（被直接问则大方承认是官方陪聊 AI 并引导继续匹配真人）」。
  • 输入 = 最近 10 条对话。写库前 sleep 1–3 秒随机延迟，先推「正在输入」状态。

§9种子数据（Bot 演员）

24 个 bot 画像写成 supabase/seed.sql。覆盖矩阵：8 款游戏 × 男女声线 × 三种风格 × 各时段，保证任何一句需求都能匹配到「像回事」的人。

生成规则（编码代理用脚本或 LLM 批量生成后固化进 seed.sql，不要运行时现生成）：昵称要像真实玩家（例：「野区养猪户」「凌晨四点的枪声」「奶但不带脑子」），每人 intro 写 2–3 句人设（口头禅、上分目标、雷点），标签互相呼应。示例三条：

  • 「凌晨四点的枪声」· 男 · 低音炮 · 三角洲行动(突击/钻石) · 激进 · 深夜 · INTJ · intro：夜班下了才上号，只打排位，能开麦优先。
  • 「奶但不带脑子」· 女 · 甜妹音 · 无畏契约(辅助/白金) · 娱乐 · 晚间 · ENFP · intro：技术下饭但气氛担当，输了不准骂人。
  • 「Steam仓鼠」· 保密 · 不开麦 · Steam杂食(肉鸽/合作) · 稳健 · 周末 · intro：库里 400 个游戏玩过 40 个，找双人成行/雾锁王国搭子。

另建 2 个「彩排真人」账号（队友 A / 主讲 B 的预设画像），彩排模式下固定互配（§12-R5）。

§11验收清单

  • □ 手机浏览器全流程走通：onboarding → 输入一句话 → 出卡片 → 聊天，全程无需说明书。
  • □ 两台不同设备（不同网络）可互相匹配并在 3 秒内互见消息。
  • □ 三类输入各测一句：「随便来个搭子」「想打瓦」「找个稳健的女生周末双排原神，最好甜妹音」—— 解析标签均正确，卡片理由引用了双方真实标签。

  • □ 「换一个」不会重复出人；候选耗尽时提示并复位。
  • □ 和 bot 聊 5 轮，回复符合人设、有拟人延迟、不穿帮。
  • □ 关掉 Realtime（开 POLL_MODE）聊天仍可用。
  • □ 断网重连后会话不丢（localStorage + 服务端数据都在）。
  • □ 彩排模式开关验证过：固定剧本可复现 §3 全部 beat。

§13开放问题 —— 你们还没回答的事

按苏格拉底的方式：我不给答案，只指出每个问题为什么绕不过去。Q1–Q4 影响今天的代码，最好开工前 10 分钟拍板；Q5–Q10 是演示问答与产品层面的「未知的未知」，答案写进讲稿。

Q1它叫什么名字？

「游戏搭子」是品类不是品牌。名字要出现在 slogan、匹配卡片、愿景页和你们的讲述里 —— 现在不定，今天下午每个界面都要留白。一个测试：观众散场后向朋友转述时，会说「我今天看到一个 ___」？

Q2演示的「舞台」到底在哪里？观众是看客还是玩家？

你们默认了「投屏 + 两台真机」，但没讨论：现场是什么网络？允许观众扫码进来吗？观众一进来，匹配池、内容安全、网络带宽全变成现场变量 —— 开放度每加一档，惊喜和翻车概率同时翻倍。这决定 R3/R6 要做多深。

Q3匹配是「翻牌直连」还是「双向同意」？

Soul 是匹配即进房，探探是双向 like 才通。你们讨论里默认了前者（对 demo 有利：无等待、无冷场），但这意味着任何人都能不经同意地「聊到」任何人 —— 演示时如果有观众问「女生会不会被骚扰到卸载」，你们的回答是什么？这个回答反过来定义正式版的匹配机制。

Q4对面是 AI，要不要告诉用户？

Bot 兜底是 demo 的保命符，也是伦理雷区：演示时如果把 bot 当真人展示而被观众识破，产品诚信全场归零。本计划的默认策略是「不主动声明、被问必承认」（§8-C），且演示词里主动把 bot 讲成「冷启动期官方陪聊」的产品特性 —— 你们接受这个策略吗？还是卡片上直接标「AI 搭子」？

Q5Demo 的终点在哪里 —— 聊上了，然后呢？

用户的真实目标不是聊天，是「今晚有人陪我打游戏」。你们的演示停在互发消息，离「开上黑」还差最后一公里（交换游戏 ID？一键组队口令？）。演示可以不做，但讲稿里要能回答「聊完之后呢」，否则整个闭环缺一个句号。

Q6冷启动：上线第一周，真实用户打开 App 匹配到的是谁？

Bot 能救 demo，救不了产品 —— 靠 AI 陪聊留住的用户不是来找 AI 的。双边市场先有鸡还是先有蛋：你们打算从哪个「单一游戏 × 单一城市/社群」切入密度？（会上反复提三角洲，是直觉还是决定？）

Q7安全与信任：女性用户第一次被语音骚扰发生在第几天？

语音社交 + 陌生人匹配 = 骚扰问题不是「会不会」而是「多快」。举报、拉黑、禁言、声音标签造假……这些不用今天做，但评委/投资人几乎必问。你们要有一页答案：先做哪三件事？

Q8合规：实名认证、未成年人、个人信息，红线在哪？

国内上线社交产品绕不过：网络实名（后台实名前台匿名）、未成年人防沉迷与社交限制、个保法下收集性别/声音/MBTI 的告知同意。愿景页写了「认证真人」，被追问认证方案时你们的口径是什么？

Q9竞品一句话：比心、TT 语音、Soul、小红书搭子群都在，你们凭什么赢？

你们真正的差异化假设是「自然语言 + LLM 理解式匹配 > 标签筛选式匹配」。这是 feature 还是护城河？如果比心明天也加一个输入框呢？想清楚这题，答案大概率落在「数据飞轮：聊天与战绩沉淀出别人拿不到的搭子画像」—— 但要你们自己说出来。

Q10散场之后：这个 demo 的「成功」如何度量？

是评委打分、拉到资源、还是决定要不要真做下去？答案决定今天下午的取舍 —— 如果是后者，与其打磨音效（M5），不如把 §13 的 Q6/Q9 想透，甚至现场收集观众「你愿意为它付 10 块/月吗」的举手数据。
